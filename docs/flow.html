How a spoken question becomes a spoken answer

This page answers: what runs where in speech-to-speech, how one voice turn moves through it, and where the 2.89 s before the first reply audio go.

TL;DR. One server process loads four models, then runs each pipeline part in its own Python thread. Plain queue.Queue objects join the threads. Audio arrives over a WebSocket. VAD waits for the speaker to stop. STT turns the audio into text. The LLM streams a reply in batches of 3 sentences. TTS turns each batch into small 32 ms PCM blocks, and the server streams them back. In the Stage 0 run, the first reply audio reached the client after 2.89 s (p50). Of that, about 0.96 s is the 900 ms silence wait the eval client asked for, and 1.40 s is the LLM writing its first 3 sentences.

Every box with a blue fill is a handler. ThreadManager.start gives each one a threading.Thread (). Each thread runs the same loop in BaseHandler: take one item from its input queue (), run process() (), and put each result on its output queue ().

1. Startup and model loading

Question: what happens between typing speech-to-speech serve and the server accepting a client?

  • All models load one after another on the main thread. No handler thread starts until every model is loaded and warmed up.
  • Times come from the Stage 0 server.log. That was the first launch, so they include model downloads.

2. One normal voice turn, end to end

Question: which thread, queue and function does one question pass through, and what does each step cost?

  • Times are Stage 0 p50 over 40 turns, plus one real turn from the log (question 3 of 40).
  • Several stage times can overlap, so you cannot just add them up. The timeline shows how they line up.

3. Streaming: tokens → sentences → TTS chunks → audio

Question: why does audio start before the LLM has finished, and what sets the size of each piece?

  • Four batching points set the first-audio time: the 3-sentence batch, the TTS model chunk of 8 codec tokens (about 640 ms of audio), the 512-sample PCM block, and the send batch of up to 6400 bytes.

4. Turn end: how VAD decides you stopped

Question: when does the server decide the user finished, and why is vad_decision exactly 0.96 s in every Stage 0 turn?

  • Silero scores each 32 ms chunk. A turn ends after enough quiet chunks in a row. Smart Turn then decides how long to hold the reply in case the user starts talking again.

5. Interruption (barge-in)

Question: if the user talks while the assistant speaks, what stops and what is kept?

supported Barge-in exists and is on by default (session turn_detection.interrupt_response, ). The server mic path is never muted: nothing in the code calls should_listen.clear().

6. Modes: serve, local, talk (WebSocket or WebRTC)

Question: what is different between running the server, the all-in-one local mode, and a client?

No raw socket mode. The code has no socket receiver or sender. A search for socket_receiver, SocketSender and websocket_server returns nothing. The old --mode realtime|local flag still parses but maps to serve / local (). Every mode uses the same OpenAI Realtime protocol.

7. Chat history

Question: how does the model remember earlier turns, and what happens to a reply that was cut off?

supported Each WebSocket session has one Chat object. The Stage 0 eval opens one connection per question (), so every question started with an empty history. Each request was 460–549 input tokens: the instructions plus one question.
